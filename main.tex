\section{Introduction} \label{sec:intro}
This evidence looks at finding a finite automaton to accept a provided regular language as also described in \cite{stakano_formal_languages}. 
The resulting automaton can then be either modeled using Prolog or REGEX as for example done in \cite{g4g-desfiniteautomaton}.
The language chosen for this evidence posesses the alphabet $\Sigma = \{0, 1, 2\}$, needs to end in either "111" or "122" to 
transition into an accepting state and prohibits the occurence of "211".
\section{Automaton} 
As \cite{hopcroft2001introduction} mention, (deterministic) finite automaton are useful models for different tasks, including lexical analysis.
When interpreting finite automatons as transition graphs, this can be easily visulaized.
A string can be broken down into each letter, which can be used to follow a graph into a specific node/ state.
In \cite{hopcroft2001introduction} a deterministic finite automaton is defined as a
quintuple $A= (Q, \Sigma, \delta, q0, F)$ where
\begin{itemize}
    \item Q defines a finite set of states,
    \item $\Sigma$ a finite alphabet,
    \item $\delta$ a transition function,
    \item q0 the inital state and
    \item F the accepting states.
\end{itemize}
As indicated in \cite{stakano_formal_languages}, an automaton of this kind parses a string by transitioning to different states of the automaton 
according to the transition function given the characters of the input string. In \cref{fig:example_automaton} a basic example of passing a binary string is given.
An input gets accepted if, after passing the string, it ends up in an accepting
state, otherwise it is rejected.

In \cite{hopcroft2001introduction} the existence of non-deterministic finite automaton is mentioned, But as further explained, a non-deterministic model has to be converted to a deterministic model,
in order to be implementable.
Due to the small size and lower complexity of the language mentioned in \cref{sec:intro}, a deterministic model approach was possible and therefore chosen,
to reduce complexity.

\subsection{Modeling the language}
Each string should start out at the same entry state E, so $q0=E$. From there one can derive the different conitions path, the automaton needs to recognize.
In \cref{fig:base_model} a first model is depicted that encodes all paths that are important for acceptance and rejection and therefore also determines all required states. The path s1e-s1f shows the accepted ending sequence "111", 
s1e-s2f models the accepting end string "122" and s3e-s3f show the rejected sequence "211". With this F is defined as $F=\{s1f, s2f\}$. This graph is incomplete, as each sate needs to have a transition for each symbol in the alphabet. 
In \cref{fig:full_model}, the full model is shown with all connections. \Cref{fig:full_model} further implies Q and $\delta$. Important to observe is, that each occurence of "0"
loops back to node E as "0" is no part of a "determining" sequence and that once s3f is reached, all further transitions loop back to the same state. 
This is because once this node has been reached, the string cannot be accepted, as the only way to reach this node is through the sequence "211". Also important are the
transitions between different branches, as each subsequence in a branch can potentially be the starting point of a different "determining" sequence.

\section{Prolog}
One method to implement the model is using Prolog. Due to the nature of prolog,
the model can be easily implemented using the visual representation.
It is only necessary to define the transitions and acceptance states:
\begin{lstlisting}
move(e, e, 0).
move(e, s1e, 1).
move(e, s3e, 2).

move(s1e, e , 0).
move(s1e, s11 , 1).
move(s1e, s21 , 2).

move(s11, e , 0).
move(s11, s1f , 1).
move(s11, s21 , 2).

move(s1f, e , 0).
move(s1f, s1f , 1).
move(s1f, s21 , 2).

move(s21, e , 0).
move(s21, s31 , 1).
move(s21, s2f , 2).

move(s2f, e , 0).
move(s2f, s31 , 1).
move(s2f, s3e , 2).

move(s3e, e , 0).
move(s3e, s31 , 1).
move(s3e, s2e , 2).

move(s31, e , 0).
move(s31, s3f , 1).
move(s31, s21 , 2).

move(s3f, s3f , 0).
move(s3f, s3f , 1).
move(s3f, s3f , 2).

accepting_state(s1f).
accepting_state(s2f).
\end{lstlisting}

The parser provieded in the lecture is used to parse the string recursively letter by letter.
\begin{lstlisting}
parseDFA(InputList) :-
    parseDFAHelper(InputList, e).
parseDFAHelper([], CurrentState) :-
    accepting_state(CurrentState),
    write('Accepted'), nl;
    write('Rejected'), nl.
parseDFAHelper([Symbol|Rest], CurrentState) :-
    move(CurrentState, NextState, Symbol),
    parseDFAHelper(Rest, NextState).
\end{lstlisting}
The helper function separates out each symbol and uses the symbol to match a
$move$ clause definition to obtain the new state.
The full script, including the test cases can be found in "dfa.pl".

If given a string of length $n$, the tail recursion algorithm looks at every symbol only once.
Therefore, the algorithm is in $O(n)$.

\section{REGEX}
"REGEX", short for "regular expression" is according to \cite{hopcroft2001introduction} an algebraic description of languages.
They further proof that any language that can be represented using a deterministic finite automaton, can also be represented using 
regular expressions. Designing a regular expression is different than designing an automaton.
Instead of thinking in individual states, one starts out by breaking the language down into individual patterns
to then string them together. In this case we can start out with the easiest condition:
The string has to and in either "111" or "122". In regex this can be denoted as 
\begin{lstlisting}
    (111|122)$
\end{lstlisting}
Here the "\$" enforces the string to end in the prior pattern.
Before this pattern, any pattern that doesn not contain "211" can be used.
This case can be broken down into 6 different patterns that can be repeated infinetly to build any valid pattern using $*$. 
Combined with the previous pattern and the addition of a special case, the regular expression results in:
\begin{lstlisting}
^(0|1|20|22|212|210)*(2122|111|122)$.
\end{lstlisting}
Note the special ending sequence "2122". As the first part can have any number of 1s and the sequence can end in "111",
adding a single "2" in the first part, would allow for the acceptance of invalid patterns. The only case 
where "21" would not raise a potential concern is when the string ends in "122". Thus the ending sequence "2122" has to be matched separatly. 
The "\string^"-symbol forces the beginning of string to also start with any of those patterns,
forcing REGEX to consider the entire string for matching and not just parts.


\section{Tests}
To test both implementations, test cases have been derived to test various situations.
The cases have been divided into two catergories: Strings that should be accepted and string that should be rejected.
\subsection{Accepted}
Here the cases 1. and 2. validate the base cases, where only the ending sequence occurs. 
Cases 3., 4. and 6. test more complex cases, with longer strings. Cases 5. and 7. are specifically
designed to test switching inbetween sequences, for example in 5., although the ending sequence "111" fully appears, 
the actual ending sequence "122" has to be identified. 
\begin{enumerate}
    \item 111
    \item 122
    \item 1122
    \item 00120122
    \item 111111122
    \item 01201201111
    \item 112122
\end{enumerate}
\subsection{Rejected}
The rejection cases test either the end sequence such as cases 1. and 4. or the occurence of "211" which is tested in all other cases.
Case 3. shows an interesting problem for REGEX, as the sequence "2122" needs to be accepted, but the sequence "2111" needs to be rejected.
\begin{enumerate}
    \item 1112
    \item 211
    \item 01201202111
    \item 00121222
    \item 001211222
    \item 11112110111
    \item 2110102001221200122
\end{enumerate}

While the tests don't enumerte every single possible case, they test every switch of sequence/ branch and some combinations of those.
These tests and parts of tests can be used to construct any other string.

\section{Comparison and Learnings}
Both methods can be used to solve the task of lexical analysis. 
But both trade interpretability for implementation complexity.
Using Prolog and deterministic finite automatons leads to easy interpretability by humans,
as describing the process in a graph allows for easy understanding. But this methods becomes very
inconvenient for increasingly complex cases, as more connections have to be drawn and denoted as the alphabet
or specifications increase. Here, REGEX is more scalable, enabeling the notation
of very complex cases in a single line of algebraic description. But this comes at the cost
of interpretability, as those description become hard to read and understand the more complex they get,
giving more space for implementation error.
